# ddflow 规划与任务约束指南

> 供 Planner 按需加载；不是新的执行引擎或业务节点类型。

## 1. 首先确定可验收的交付

先问清“怎样才算合格”，再安排模型分工。记录用户提供的目标、输入、允许的输出范围、不可改变的信息、数据访问边界、可用 Harness 和模型。已知信息不要重复询问；未知而不阻塞结构设计时先列为待绑定，不编造细节。

如果问题只需一个现成脚本，就直接说明不需要复杂工作流。ddflow 的价值不能建立在给简单任务增加 Agent 数量上。

## 2. 模型分工的规划方式

按任务的不确定性、错误后果、能否程序化验证、所需上下文和工具能力选择模型。不只凭模型品牌决定分配。

先用能力语言提出安排，例如“规则设计需要强判断；批量执行用适合的模型；格式检查交脚本”。拿到真实模型目录后再填写 model，不能把 `cheap-model` 之类占位符作为已配置引用。

宿主支持且具体取值可核实时，主动在节点填写 reasoning_effort 并说明选择依据；它与 model 同为显式绑定。省略表示接受已披露的默认强度，不填占位符或自动补 medium。只指定强度而省略 model 时，核对默认模型的支持情况。不同模型的同名强度不等于相同计算量；不维护通用强度映射。执行前确认 Executor 理解这个字段。

优先遵循：已有规则 → 工具批处理；规则内有限判断 → 适合的模型；规则制定 / 高风险歧义 → 更有能力的模型或用户决策。复核不一律使用最强模型，按风险与证据决定。

避免为每个小动作启动新 Agent，避免每波把整个数据集和全部计划再次放入会话。长产物作为文件交接，摘要只保留必要事实。

### 规划阶段的执行准备

规划优先由较强模型完成规则设计、方法选择和验收设计，经济协调模型接手后主要按契约推进。Planner 的实际模型由用户或宿主原生配置选择，不通过提示词自称切换，也不新增模型路由。用户指定的模型安排优先，未确认的能力与配置如实披露。

把已确定的决策落实为可直接使用的材料，优先引用可信现有实现；没有必要时不另写脚本。可以在用户指定的仓库外业务工作区准备规则文件、执行脚本、固定校验器和少量判断例子，不处理真实业务数据、不启动节点、不试跑所准备的业务程序、不安装依赖。允许已授权的只读资料检查，以及不执行业务代码的语法 / 静态检查；单独的程序试跑或数据实验需要用户另行明确要求。检查的文件与日志也留在该业务工作区，不写 DDFlow 源码仓库。

使用现有正文交接，不新增 Schema 字段、材料注册表或完成节点：

| 位置 | 准备内容 |
|---|---|
| workflow 的 Execution Notes | 材料路径、用途与来源，已做检查及其范围，未验证事项和执行前提 |
| 节点 Inputs | 所需规则、脚本、校验器的确切路径；区分已有材料与上游执行后才生成的产物 |
| 节点 Prompt / Outputs | 调用命令、参数、输入输出约定、允许的实现调整和遇到范围外情况的处理方式 |
| 节点 Completion Criteria | 实际检查对象、检查执行者、通过条件及证据交付；语义判断安排到既定复核节点 |

准备好的文件作为已有输入，不为表示准备进度创建 completed 节点。新节点仍初始化 pending，Result / Error 留空；语法检查通过不表示脚本运行成功或业务验收通过。规则和固定校验器对使用它们的 worker 只读；执行脚本能否修改及写到哪里由 Contract 明确，允许局部实现修复也不能改变业务规则或验收器。

未知字段、业务口径或数据特征不能靠规划模型猜定。影响正确性且无法留待执行的问题先澄清；依赖运行后新事实的部分，安排明确的准备 / 规则节点及其验收，下游用 depends_on 声明真实依赖。若其结果超出既定政策且无法依约继续，按失败与显式 Re-plan 处理，不让经济协调者临时设计业务规则。

已知顺序、分支和结果筛选可以写入节点内程序，或复用宿主已有的程序化工具调用能力，减少逐步模型往返。只向模型返回必要摘要、异常与证据路径，完整证据留在业务目录；不能吞掉失败来缩短输出。不得把跨节点 DAG 合成一次不经节点验收的长调用，不绕过每次派发前检查、每波重读和失败停图。不自研 PTC Runtime，也不承诺未经实测的成本收益。

可用下面的要求指导规划，按任务缩减，不逐节点复制：

> 你的交付对象包含一个主要负责协调的经济模型。尽量消除执行者需要重新推导的业务决策，为节点准备明确的输入、输出、执行方法、必要上下文与验收证据要求。能由确定性程序完成的工作，优先提供可信程序或可直接使用的调用说明；必须依赖语义判断的工作，安排明确的 Agent 节点。分开记录事实、假设和执行时才能确认的问题；已准备、静态检查通过与实际业务验收通过必须区分。

### 验收分工

主 Agent 只负责派发、依赖与失败边界，以及最小交付和证据核对，不承担业务内容复核。可以为该职责选择经济模型，但仍需具备可靠的原生派发、文档操作和协议遵循能力；不能在未实测时声称节省比例或执行可靠性已得到保证。

在现有 Completion Criteria 中写清检查由谁执行、检查对象、方法、通过条件及返回什么证据，不新增 Schema 字段：

| 检查内容 | 执行安排 | 主 Agent 读取 |
|---|---|---|
| 格式、来源覆盖、金额汇总、产物之间的一致性 | 处理或验收节点调用固定程序 | 对应当前产物与规则的运行结果、退出状态及证据路径 |
| 分类合理性、歧义处理、报告结论等业务判断 | 预先规划的复核节点，按任务选择模型 / 子 Agent | 逐项结论、约定范围覆盖情况、未通过项与证据路径 |
| 返回归属、文件可访问、证据齐全及明确门槛是否满足 | 主 Agent | 必要摘要与定位信息，不重读业务正文或复判样本 |

确定性检查可在处理节点内部完成，不为每条规则另建节点。需要语义复核时才安排独立的 Agent Task，允许一个复核节点覆盖多个上游产物；通过 depends_on 声明依赖，不设置动态评审或隐式第二轮验收。复核者按既定范围读取业务内容、执行抽样并提供明确结论，不把判断再次交回主 Agent。

候选处理节点只承诺候选交付与自己的检查；后续复核节点承诺约定的质量判断。例如“候选表与映射结构通过固定检查”可先完成，随后复核节点检查语义质量；不能让处理节点必须等下游复核完成才完成，也不能在执行时把原本承诺最终合格的节点改称候选。最终交付依赖所有必需复核并提供针对最终文件的检查证据，主 Agent 不在其后再做相同检查。纯确定性任务无须增加语义复核节点。

## 3. 最小充分 DAG

拆节点必须有明确理由：更换模型能力、稳定的中间产物、独立验收、风险边界、安全并行或必要的汇合。多个同质小动作可以在同一节点内批量处理。

不固定节点数量；不把读取 / grep / 转换 / 写入机械拆开。一个节点内部可以自主使用多个工具，但自主权不能越过 Contract。

所有真实前置通过 depends_on 表达。并行还要检查工作区写冲突；两边同时改同一张表、规则文件或报告模板时应串行，或各写独立候选产物后再合并。

## 4. Worker 节点必须写清什么

| 维度 | 最小要求 | 不合格写法 |
|---|---|---|
| 输入 | 实际文件位置、字段语义、必要上游产物 | “读取相关资料” |
| 规则 | 可执行的映射、允许操作、边界例子 | “智能清洗” |
| 自主范围 | 可以推断什么、什么必须留待复核 | “自行决定最合理的结果” |
| 输出 | 目标文件、字段、来源对应关系 | “保存清洗后的结果” |
| 异常 | 哪些允许单列、哪些导致节点失败 | “有问题就跳过” |
| 验收 | 实际命令 / 检查项 / 样本与阈值 | “确认没有问题” |

按需给少量正例与反例，不把规则写成难以遵循的长篇背景。对低能力模型，先缩小任务边界与工具选择；不是无条件加长 Prompt。

### Contract 编写示例

从用户需要的交付倒推：哪些可观察事实必须成立、哪些产物支持这些事实、如何核对产物之间的关系。把检查执行者、对象、方法、通过条件与证据交付写入现有 Completion Criteria；规划阶段可准备检查程序，不填写节点运行结果。验收使用准备材料时绑定实际路径；依赖规则节点时，明确其产物与依赖，不能提前编造业务阈值。

例如，目标为“交付可追溯的标准交易表”时，可按已确认业务规则写成：

| 可观察事实 | 检查对象与方法 | 通过条件 |
|---|---|---|
| 每条输入记录都有去向 | 对输入来源 ID 与保留、排除、合并映射做集合核对 | 无未知丢失；去向符合约定的互斥与覆盖规则 |
| 来源映射指向实际结果 | 核对映射中的目标 ID 与最终标准表 | 无悬空引用，合并关系符合固定规则 |
| 质量报告描述当前交付 | 从最终表、映射和异常清单重算约定统计 | 报告与重算值满足已约定精度 |

字段、精度和异常政策须绑定到真实任务，不能照搬示例充当已确认规则。文件存在或处理脚本退出成功，均不能单独证明上述目标。

Prompt 要区分实现自主权与业务决策权。例如：“可自行选择批处理方法；币种缺失时不得猜测，按规则文件指定的待复核政策处理。”若政策尚未明确且影响正确性，先澄清或列为执行前提；不要把所有实现选择都变成用户审批。

## 5. 数据清洗专用约束（仅作为参考方案）

原始输入只读，清洗写新目录。每条记录保留稳定来源标识；跨表合并、去重或聚合时，输出与原始记录可以是一对多 / 多对一，但映射必须可审计。

完整性不应机械要求“清洗前后行数相等”。应核对：每个原始记录被保留、明确排除、或有合并映射；没有未知的丢失 / 重复。行级分区统计需互斥且完整，聚合结果通过来源映射核对。

结构验收可包括字段 / 类型 / 唯一性 / 缺失值政策 / 合法范围 / 编码。业务约束由用户目标与已确认规则决定，不将空值一律补零、不随意删异常、不推断敏感属性。

语义任务保留原文与证据，输出候选与待复核列表。异常列表是原 Contract 允许的业务产物，不是把所有失败都吞掉的垃圾桶。限定允许的未决范围并在最终交付说明。

既定复核节点同时看待复核记录和处理 worker 自判正确的分层样本，主 Agent 不再次抽查。固定金标准不能从当前 worker 的答案生成；验收器不能由被验收的 worker 修改。最终交付节点执行针对最终数据的全局检查，主 Agent 核对其证据，不只引用中间结论，也不重复执行最终检查。

大文件不整表进入模型上下文。先以程序生成 profile / schema / 抽样，再只向模型提供需要语义判断的部分；批次划分属于节点内部实现，不增加动态 DAG 或通用 MapReduce 引擎。

## 6. Skill 和自定义 Subagent

只有用户指定或能够核实存在的 Skill / Agent 才写入 YAML。Skill 是方法与资料，Agent 是宿主的执行配置，model 是能力选择，三者不互相替代。

配置 skills 后，执行时必须检查 worker 真正能加载。不可假设主 Agent 使用了统计 Skill，子 Agent 就已经拥有统计规范。必要时给受信任的规则 / 参考文件路径，而不是引入额外 Skill。

第三方内容要核对版本、来源、权限与许可。安装脚本、网络请求或额外 API Key 需求必须披露，不能在用户只要求规划时自动安装。

### ZCode 预定义子 Agent

ZCode 不支持由 Skill 在子 Agent 派发时设置模型和思考强度。先了解用户已经配置的子 Agent 名称、用途与可用能力；已有信息不重复询问。需要的配置不存在时，给出最小角色需求与建议配置，请用户在 ZCode 中手动设置子 Agent，并返回真实可调用名称。不要替用户编造配置文件格式或不存在的参数，也不要自动修改宿主设置。

规划采用 `agent.recommended` 引用已定义的子 Agent，在节点 Prompt 明确“使用已配置的 <真实名称>，沿用用户设置，不退回其他 Agent”。沿用该配置时可省略 `model` 和 `reasoning_effort`，在 Execution Notes 说明配置来源与已知限制；只有用户明确要求且能通过该配置落实的值才写成显式绑定。不得把配置说明填为 `execution.*_used`。

例如用户已确认存在 `data-cleaner` 时，节点 YAML 可包含：

```yaml
agent:
  recommended: data-cleaner
execution:
  status: pending
```

这是字段片段，不是完整节点；名称必须替换为用户环境中的真实名称。尚未配置时可以完成待绑定的计划结构，正文列出执行前提，先不写虚构 Agent 名称。配置完成后由 Planner 更新 pending Contract；Executor 不自行补写指派。

## 7. Re-plan 安全

Planner 可以编辑工作流文档并准备执行材料，不产生真实业务处理结果。发现 running 节点就只读诊断，不修改文档、模型或准备材料。

只直接改 pending 的 Contract。completed / failed 保留，不重置。新尝试用新 ID，failed 只作为正文上下文；机器依赖连接真实成功前置。修复全部剩余 pending 路径，不遗留 failed ancestry。

思考强度的调整同样属于 Contract 修订；不追补历史节点的请求或生效事实，不以自动提高强度绕过失败恢复边界。

未被执行历史引用的准备材料可以随 pending Contract 修订；被 completed / failed 引用的材料必须保留，更改时写到新位置，只调整 pending 引用，已执行的受影响工作以新节点重做。需要改变规则制定节点的历史输出时，应规划新规则节点和必要下游重做，而非让旧 completed 节点的产物悄悄变为新版本。MVP 不建立产物版本平台，使用新的文件位置并保留来源即可。

## 8. Planner 完成时交付

交付工作流路径、目标和节点分工、模型 / Skill 安排依据、准备材料路径及来源、实际检查范围、需确认的未知项、验收方式与关键风险。说明哪些已经准备、哪些仍需执行节点生成，不能将静态检查描述为真实数据验证。

完成后停止，不自动执行、不自动启动花费资源的验证工作流。用户显式执行构成阶段边界，普通节点不重复设置审批流程。
