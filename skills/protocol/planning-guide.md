# ddflow 规划与任务约束指南

> 供 Planner 按需加载；不是新的执行引擎或业务节点类型。

## 1. 首先确定可验收的交付

先问清“怎样才算合格”，再安排模型分工。记录用户提供的目标、输入、允许的输出范围、不可改变的信息、数据访问边界、可用 Harness 和模型。已知信息不要重复询问；未知而不阻塞结构设计时先列为待绑定，不编造细节。

如果问题只需一个现成脚本，就直接说明不需要复杂工作流。ddflow 的价值不能建立在给简单任务增加 Agent 数量上。

## 2. 模型分工的规划方式

按任务的不确定性、错误后果、能否程序化验证、所需上下文和工具能力选择模型。不只凭模型品牌决定分配。

先用能力语言提出安排，例如“规则设计需要强判断；批量执行用适合的模型；格式检查交脚本”。拿到真实模型目录后再填写 model，不能把 `cheap-model` 之类占位符作为已配置引用。

宿主支持且具体取值可核实时，主动在节点填写 reasoning_effort 并说明选择依据；它与 model 同为显式绑定。省略表示接受已披露的默认强度，不填占位符或自动补 medium。只指定强度而省略 model 时，核对默认模型的支持情况。不同模型的同名强度不等于相同计算量；不维护通用强度映射。执行前确认 Executor 理解这个字段。

优先遵循：已有规则 → 工具批处理；规则内有限判断 → 适合的模型；规则制定 / 高风险歧义 → 更有能力的模型或用户决策。复核不一律使用最强模型，按风险与证据决定。

避免为每个小动作启动新 Agent，避免每波把整个数据集和全部计划再次放入会话。长产物作为文件交接，摘要只保留必要事实。

## 3. 最小充分 DAG

拆节点必须有明确理由：更换模型能力、稳定的中间产物、独立验收、风险边界、安全并行或必要的汇合。多个同质小动作可以在同一节点内批量处理。

不固定节点数量；不把读取 / grep / 转换 / 写入机械拆开。一个节点内部可以自主使用多个工具，但自主权不能越过 Contract。

所有真实前置通过 depends_on 表达。并行还要检查工作区写冲突；两边同时改同一张表、规则文件或报告模板时应串行，或各写独立候选产物后再合并。

## 4. Worker 节点必须写清什么

| 维度 | 最小要求 | 不合格写法 |
|---|---|---|
| 输入 | 实际文件位置、字段语义、必要上游产物 | “读取相关资料” |
| 规则 | 可执行的映射、允许操作、边界例子 | “智能清洗” |
| 自主范围 | 可以推断什么、什么必须留待复核 | “自行决定最合理的结果” |
| 输出 | 目标文件、字段、来源对应关系 | “保存清洗后的结果” |
| 异常 | 哪些允许单列、哪些导致节点失败 | “有问题就跳过” |
| 验收 | 实际命令 / 检查项 / 样本与阈值 | “确认没有问题” |

按需给少量正例与反例，不把规则写成难以遵循的长篇背景。对低能力模型，先缩小任务边界与工具选择；不是无条件加长 Prompt。

## 5. 数据清洗专用约束（仅作为参考方案）

原始输入只读，清洗写新目录。每条记录保留稳定来源标识；跨表合并、去重或聚合时，输出与原始记录可以是一对多 / 多对一，但映射必须可审计。

完整性不应机械要求“清洗前后行数相等”。应核对：每个原始记录被保留、明确排除、或有合并映射；没有未知的丢失 / 重复。行级分区统计需互斥且完整，聚合结果通过来源映射核对。

结构验收可包括字段 / 类型 / 唯一性 / 缺失值政策 / 合法范围 / 编码。业务约束由用户目标与已确认规则决定，不将空值一律补零、不随意删异常、不推断敏感属性。

语义任务保留原文与证据，输出候选与待复核列表。异常列表是原 Contract 允许的业务产物，不是把所有失败都吞掉的垃圾桶。限定允许的未决范围并在最终交付说明。

复核同时看待复核记录和 worker 自判正确的分层样本。固定金标准不能从当前 worker 的答案生成；验收器不能由被验收的 worker 修改。最后发布前重新执行针对最终数据的全局检查，不只复用中间检查结论。

大文件不整表进入模型上下文。先以程序生成 profile / schema / 抽样，再只向模型提供需要语义判断的部分；批次划分属于节点内部实现，不增加动态 DAG 或通用 MapReduce 引擎。

## 6. Skill 和自定义 Subagent

只有用户指定或能够核实存在的 Skill / Agent 才写入 YAML。Skill 是方法与资料，Agent 是宿主的执行配置，model 是能力选择，三者不互相替代。

配置 skills 后，执行时必须检查 worker 真正能加载。不可假设主 Agent 使用了统计 Skill，子 Agent 就已经拥有统计规范。必要时给受信任的规则 / 参考文件路径，而不是引入额外 Skill。

第三方内容要核对版本、来源、权限与许可。安装脚本、网络请求或额外 API Key 需求必须披露，不能在用户只要求规划时自动安装。

## 7. Re-plan 安全

Planner 只编辑工作流文档；不写业务产物。发现 running 节点就只读诊断，不修订其邻接图或模型。

只直接改 pending 的 Contract。completed / failed 保留，不重置。新尝试用新 ID，failed 只作为正文上下文；机器依赖连接真实成功前置。修复全部剩余 pending 路径，不遗留 failed ancestry。

思考强度的调整同样属于 Contract 修订；不追补历史节点的请求或生效事实，不以自动提高强度绕过失败恢复边界。

需要改变规则制定节点的历史输出时，应规划新规则节点和必要下游重做，而非让旧 completed 节点的产物悄悄变为新版本。MVP 不建立产物版本平台，使用新的文件位置并保留来源即可。

## 8. Planner 完成时交付

交付工作流路径、目标和节点分工、模型 / Skill 安排依据、需确认的未知项、验收方式与关键风险。

完成后停止，不自动执行、不自动启动花费资源的验证工作流。用户显式执行构成阶段边界，普通节点不重复设置审批流程。
